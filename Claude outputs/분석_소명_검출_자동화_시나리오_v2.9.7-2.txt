h1. LogCatch 2.9.7.0 분석(이상행위)·소명·검출 자동화 시나리오 정리

{info:title=개요}
* 대상 버전 : LogCatch 2.9.7.0_261105
* 대상 서버 : 10.10.54.21 (업데이트 설치, 자동화 전용)
* 접속 기록 발생용 시스템 : 10.10.54.27 CRM (리눅스_VIP고객)
* 스크립트 위치 : CypressWork\cypress\e2e\Basic_functions_check / Depth_functions_check
* 공통 함수 : cypress\support\anomaly.js · CRM 접속 기록 발생은 cypress.config.js 의 Node task crmTraffic (재시도)
* 메일 확인 : Mailpit http://10.10.54.26:8025 (공용 메일함 — 지우지 않음)
* 작성일 : 2026-11-11 / 수정 : 2026-11-12 (No.18~26 추가 · 6·11·12 절차 갱신 · 5·6장 추가)
{info}

{note:title=2.9.x 변경 사항}
「소명하기」 메뉴는 2.7·2.8 전용이며 2.9.x에서는 사용하지 않는다(.21은 메뉴관리에서 폐기 처리).
기존 소명하기 스크립트(UI_Module_Full_Check/05_소명하기, Basic 04·05 소명 3종)는 2.9 세트에서 제외하고 Check\v2.9.6까지만_소명하기메뉴폐기 폴더로 옮겼다. 아래 시나리오가 이를 대체한다.
{note}

h3. 1-3. 소명 결재선 정책

* 소명 > 정책 > 결재선 에 결재 유형 「소명」·「사용」 정책이 있어야 한다(.21 : 각 부서 부서장이 결재자).
* user010은 2026-11-11 UI1팀 부서장으로 지정함.

h3. 1-4. 메일 확인 환경

* .21 의 SMTP 발송 메일은 Mailpit(10.10.54.26:8025)으로 들어온다. 스크립트는 API(/api/v1/messages · /api/v1/message/<ID>)로 본문 · 첨부를 확인한다.
* 공용 메일함이므로 메일을 지우지 않고, 실행 전 메일 ID 목록과 비교해 새로 온 메일만 본다.

h3. 1-5. 소명 요청 자동화 설정 (.21)

* 2026-11-12 기준 : 자동 소명 요청 사용 ON · 미소명 임계 기간 1일 · 재발송 주기 1일 · 발송 시각 10시 · 엑셀 첨부 ON (매일 10시 자동 발송 중)
* No.20 스크립트는 시작할 때 이 값을 읽어 두고 끝날 때(실패해도 after) 되돌린다. 「사용」 스위치는 건드리지 않는다.

h3. 1-6. 검출 임시 값

* 전처리 필터링 정책 등록 시험 값은 SELECT 1 FROM auto_임시_검출_<시각> (실제 SQL 에 걸리지 않는 값). 시작할 때 · 끝날 때 auto_임시_검출_ 이 든 값을 모두 지운다.

h2. 4. 반복 실행 설계 원칙

* *조회 전용 우선* : Basic · 권한 분리는 데이터를 만들거나 바꾸지 않는다. 경보·문서가 0건이어도 통과한다(있을 때만 내용 확인).
* *시나리오별 전용 정책* : 정책 1개당 하루 1건의 경보가 생기므로(집계 1일) 승인과 반려 정책을 나눠 서로의 경보를 쓰지 않게 했다.
* *경보를 되돌려 놓는 흐름 우선* : 반려 · 신청 취소는 경보가 소명 대상 목록으로 되돌아와 같은 날 반복해도 된다. 경보를 소모하는 것은 승인뿐이다.
* *스스로 정리* : 수명주기는 시작할 때 auto_임시_ 정책을, 신청 취소는 남은 결재 대기 문서를 먼저 정리한다. 전용 정책 사용 여부는 after()에서 OFF로 되돌린다.
* *실행 순서와 무관* : it마다 스스로 로그인하므로 단독 실행·전체 실행 결과가 같다.
* *건너뜀(Pending) 처리* : 경보가 없으면 실패가 아니라 Pending으로 남긴다(테스트 데이터 소진이지 제품 문제가 아님).
* *실행 전제* : 반려 · 신청 취소 · 일괄 소명 · 부재중 위임 · 경보 건수 갱신은 같은 전용 정책(auto_소명_반려)을 쓰므로 한 러너에서 순서대로 실행한다(병렬 실행 시 서로의 결재 대기 문서를 취소할 수 있음). 현재 GitHub Actions 는 PC-Auto 러너 1대로 순차 실행.
* *공용 메일함* : Mailpit(.26)은 지우지 않고 실행 전 메일 ID 목록과 비교해 새로 온 메일만 확인한다.
* *설정 원복* : 소명 요청 자동화는 시작 때 읽은 설정으로 after()에서 되돌리고, 자동 발송 「사용」 스위치는 건드리지 않는다.
* *즉시실행 대기* : 즉시실행은 비동기(「최대 1분 안에 실행」)라 실행이력에 새 「성공」 기록이 생길 때까지 15초 간격으로 확인한 뒤 비교한다.
* *증가분 비교* : 변경 이력처럼 실행마다 쌓이는 값은 실행 전 수와 비교한다.
* *알려진 결함은 기록만* : Mantis 에 등록한 결함은 실패로 처리하지 않고 probe 관찰 기록에 남긴다(고쳐지면 확인 조건으로 바꾼다).
* *화면 구조 기록* : 단계마다 cypress/probe/D04*·D08*·B04*·B10*.json 으로 화면 구조를 남겨 실패 원인을 바로 볼 수 있게 했다.

|필터링 정책|탭 4개(사용자 IP · 화면 URI · 특정 SQL · CONTENT-TYPE 제외), 탭마다 입력 · 필터 목록 · 변경 이력(조건 글자를 누르면 「변경 이력 상세 보기」). 삭제 확인창 「삭제하시겠습니까?」 → 「삭제했습니다.」. 저장 안내도 「삭제했습니다.」(0038997), 같은 값 재저장은 목록 그대로 · 이력 Add 추가(0038998), 이력 상세 Optional.empty(0038999), CONTENT-TYPE 첫 열 머리 없음(0039000)|
|전처리 설정 트리|vue-treeselect. 항목 글자를 실제로 눌러야 오른쪽 폼에 불러옴(자동화는 realClick)|
|행위유형 관리|검색 : POST /logcatch/pams/action-type/policy-list (map.uriLike · bsnIdList · actionTypeList). URI 입력값은 입력 뒤 잠깐 있다 반영되어 자동화가 입력 직후 검색하면 이전 값으로 조회됨(사람이 하면 재현 안 됨 → 1.5초 대기). Enter 로는 검색 안 됨(개선 요청 후보)|
